# Changelog

All notable changes to this project are documented in this file.

## [1.7.8] - 2026-10-18

### Fixed (`codex-coding-agent` sessions stopped persisting from the first step)

- **The three pre-step plugins wrote the retired V3 source wrapper, and V4 admission refuses it.** `codex-environment.mjs`, `codex-permissions.mjs` and `codex-collab-mode.mjs` injected their `<environment_context>` / `<permissions instructions>` / `<collaboration_mode>` blocks as `source: { kind: 'plugin', plugin: name, form: 'snapshot', sections: [...] }`. Since session format v4, message sources are producer-owned: `source()` refuses a missing/empty `kind` and the retired `kind: 'plugin'` wrapper (`packages/session/session-format-v3-to-v4/src/message-sources.ts:9`), reached on the write path through `assertV4RowAdmission` (`packages/session/session-format-v3-to-v4/src/codec.ts:46-53`).
- **The refusal happens at JSONL encode time, so the plugins never see it and the whole write batch is lost.** `Session.append()` does not validate the source; the throw comes from `eventLine()` (`packages/session/session-persistence-jsonl/src/format.ts:322-324`). A failed batch is retained in order and sets `drainPaused` (`packages/session/session-persistence-jsonl/src/storage.ts:303-313`), so every later flush retries and fails again: title generation reports `automatic title generation failed`, the projection cache reports `cache stays stale`, and the session log stops at its last successfully written row. No bad row ever reaches the jsonl, so nothing needs migrating or cleaning.
- **Fix: `kind: name` — the producer's own name — and the retired identity field is gone.** `form: 'snapshot'` and `sections` stay: they are still the current `ContextFormed` vocabulary (`packages/llm/llm/src/message.ts:86-94`) and V4 preserves them verbatim. Deliberately NOT done: relaxing DSH's admission (it is an intentional integrity check), writing `kind: 'plugin:<name>'` (that prefix is the V3-to-V4 migration's internal form for historical rows), or waiting for a DSH upgrade (the check is identical in `0.2.0-rc.2` and `0.2.1-rc.2`). Historical sessions are unaffected: their rows migrate to `plugin:codex-environment` and friends (`packages/session/session-format-v3-to-v4/src/sources.ts:58-65`), both kinds are admitted, and consumers keep unknown kinds visible by kind (for example `packages/client/ui-chat/src/client/conversation-nodes/event-projection.ts:71-74`).
- **Pinned at the wire level, not by inspection.** A throwaway check (`.scratch/check-message-source.mjs`, not published) drives each preset's real `agent/pre-step` listener against a stub context and feeds the emitted message to `sessionFormatCatalog.encodeCurrentEvent`: all three now encode as `"kind":"codex-environment"` / `"codex-permissions"` / `"codex-collab-mode"`, while the retired wrapper still throws `producer-owned source kind` (the rule `packages/session/session-format-v3-to-v4/tests/message-sources.spec.ts:37-54` pins upstream). `rg "kind:\s*['\"]plugin['\"]"` is clean in this repo.
- **Deployment note:** a profile that installs this package from GitHub pins a commit snapshot, so editing the checkout — or restarting alone — does not change a live profile. Re-resolve the dependency (a new sha/branch, or a `link:`), confirm the installed `presets/codex-coding-agent/*.mjs` show `kind: 'codex-environment'`, then restart the host: presets load at startup and a browser refresh is not enough.
- The same retired wrapper still exists in sibling packages outside this bundle (`dsh-custom-tool-fs` `read-image`, `dsh-user-approval` `smart-classifier`, `dsh-auto-approval-llm`, `dsh-auto-review`, `dsh-auto-approve`). They live in separate repos and are not fixed by this release.

## [1.7.7] - 2026-10-18

### Changed (`chat-subagent`'s top-level catalog now lists only the delegation tools)

- **The root session no longer sees the preset's tool rows.** `chat-subagent` mounts the `read`/`glob`/`grep`/`todo_*`/`job_*` rows because the delegated child inherits them, and every one of them used to appear in the top-level session's catalog and be refused only at call time. As of this release a depth-0 **catalog mask** — `ctx.tools.restrict({ allow: [] })` on the **Agent's own scope**, installed by `presets/chat-subagent/delegator.mjs` for each live depth-0 agent and lifted when the agent leaves the preset or is disposed — hides the inherited rows, so the root catalog is exactly `subagent` + `list_subagent_models`. That works because `ToolRuntime.view()` filters only the surface a scope INHERITS and always overlays its own-layer registrations; the model-selection opt-in puts both delegation tools in that own layer.
- **The mask is catalog only, never enforcement, and never reaches a child.** The single standing guard is unchanged and still refuses every call outside the two names. The mask is on the Agent scope, not the preset plane: a preset-plane restriction would also be on the delegated child's scope chain (the child joins its parent's preset) and a restriction can only narrow, which would leave the child with no tools at all. The child's scope parent is the preset's standing scope, so it inherits neither the mask nor its lift.
- **The mask is installed one macrotask late, coalesced, and lifts the same way.** `restrict()` notifies `tools/change`, where `guard()` does not, and the official delegation plugin installs into a live Agent on exactly that event. Installing it synchronously from `agent/created` reproduced the 1.7.3 collision (`tool "list_subagent_models" is already registered in this scope`, `install()` aborted, session left with no delegation tool). The flush is therefore a single `setTimeout(..., 0)` for all pending agents, so none of this plugin's `restrict()` calls land inside a creation or switch dispatch. Reading a catalog inside the same tick as `sessionController.create` still shows the inherited rows; the next macrotask does not. Lifting is deferred the same way.
- **Failure modes are fail-soft.** No `tools.restrict` on the runtime, a runtime without the `agents`/`agentPresets` services, or a `chat-subagent` mount without `presetId`, and the plugin never masks (the guard still enforces). A different preset for the same agent lifts the mask. The row's dispose hook clears the pending flush and lifts every persona and mask it installed.
- **The residual is the same own-layer caveat as `chat-agent`:** a profile that mounts the agent-team bundle registers its nine Team tools in each root Agent's own layer, which no restriction filters. Those stay visible in the catalog and the guard refuses their calls. Hiding them would need a DSH-side own-layer seal.
- **Checks and docs.** `check-delegator.mjs` now asserts the mask lifecycle: the standing scope gets NO `restrict()` (that would strip every child), each depth-0 agent gets exactly one `{ allow: [] }` install, a child gets none, the install happens one tick after `agent/created` (not synchronously), it lifts on `tools/change` when the preset changes or `presetId` is absent, and a missing or throwing `restrict` warns instead of failing the mount. The READMEs, `CONTEXT.md` (new term: catalog mask), `TODO.md`, `PUBLISH-CHECKLIST.md`, the delegation note and the preset header now describe the catalog instead of the old "the catalog is the whole preset" claim.

## [1.7.6] - 2026-10-18

### Fixed (`chat-subagent` lost both delegation tools on a preset switch)

- **The preset-switch defect is now pinned to a listener-order race, and this release routes around it.** A new Web session is created on the default `standard` preset and then applies the picked preset through `agentPresets.select` → `recompose`, which rebinds the Agent's scope parent and emits ONE `tools/change`. Every preset's `@deepseek-ai/dsh-tool-subagent` instance receives it in **listener registration order**, which is preset **mount order**. The outgoing preset's per-Agent removal is asynchronous (`fiber.dispose()`); the incoming preset's install is queued into a fiber callback. If the incoming listener runs FIRST, its `list_subagent_models` registration collides with the outgoing copy still installed in the same Agent scope: `install()` aborts before `mount()`, the failed fiber stays cached in `scopedInstalls`, and the session keeps neither tool.
- **Measured listener order (real `dev_web` composition, in-process, no server started):** `chat-subagent` 2, `standard` 3, `ptc` 4, `cordis` 5, `codex-coding-agent` 6, `iflow-coding-agent` 7, `iflow-cre-agent` 8, `pair-coding-agent` 9, `qwencode-coding-agent` 10. Rule: a switch fails exactly when the incoming preset's index is lower than the outgoing one's.
- **This was never specific to our preset.** Reproduced with shipped presets only: `cordis → standard`, `cordis → ptc` and `pair-coding-agent → standard` all lose the tools with the same duplicate error. The coding presets won the directions tested earlier only because they sit after `standard` in mount order.
- **Why `chat-subagent` always lost:** it was the only preset whose delegation row was a TOP-LEVEL row. A group's children mount later than top-level rows, so the top-level row put our listener first (index 2, before `standard` at 3) and every switch INTO this preset was "incoming before outgoing". Removing the `delegator` row did not change it; only the row's position did.
- **Fix: the delegation row now sits inside a `cordis:group` (`isolate: {workflowEngine: true}`), the shape the coding presets already used.** Re-measured: our listener moved from index 2 to LAST (9th of the 9 delegation instances), the outgoing removal now runs first, and `standard → chat-subagent` and `ptc → chat-subagent` both keep `subagent` + `list_subagent_models`. The post-switch schema still carries `provider`/`model`/`reasoning_effort`, the preset is not broken, and `standard → pair-coding-agent` is unchanged.
- **Known cost, documented in the preset header and `TODO.md`:** the reverse direction now loses instead. Re-picking a different preset on a still-blank session (e.g. `chat-subagent → standard`) resolves the tools of the preset being entered. Open a new session after changing the pick. This is a workaround, not a fix: the durable fix belongs in `@deepseek-ai/dsh-tool-subagent` (do not cache a failed per-Agent install so the next `tools/change` retries; wrap `removeScoped`'s `fiber.dispose()` in `Promise.resolve(...)`), and remains recorded as an upstream item.
- **`check-subagent-model-selection.mjs` now pins the row inside the group.** It asserts the `delegation` group carrier and that the row's indentation is deeper than `delegator`'s, so a future edit cannot silently move it back to the top level.

## [1.7.5] - 2026-10-17

### Fixed (diagnosis corrected: the collision is a preset-SWITCH ordering defect, not our restriction)

- **1.7.4's explanation was incomplete, and it is now measured.** Removing every `restrict()` did NOT remove `[E] scope Error: tool "list_subagent_models" is already registered in this scope`: a fresh `dev_web` session still printed it and still ended with `unknown tool "subagent"`. A temporary `info` diagnostic — added for this measurement and removed again in this release — printed, on every `tools/change`, each Agent's preset plus whether `subagent` / `list_subagent_models` resolve in its catalog. It showed the real trigger: **switching the preset of a live session**.
- **Measured sequence.** A new web session is first composed with the default `standard` preset and then switched to the picked one, and `standard` also carries `modelSelectionSettings: true` — so it has already registered the global `list_subagent_models` into that Agent's own scope. On the switch, if the INCOMING preset's per-Agent install runs before the OUTGOING preset's fiber finishes disposing, the registration collides (`registerListSubagentModels()` ← `install()` ← the `agent.ctx.inject()` callback, `@deepseek-ai/dsh-tool-subagent` `src/index.ts:676`); `install()` aborts before `mount()`, and the outgoing teardown then removes what is left, so the session has NEITHER tool. The failure is also remembered: `scopedInstalls` caches the fiber, so `installScoped()` never retries.
- **Control, same run.** `standard → pair-coding-agent` and `standard → iflow-coding-agent` printed the disposal (`subagent=false lister=true` → `lister=false`) BEFORE the install (`lister=true` → `subagent=true`) and worked, child delegation included; `standard → chat-subagent` printed the install attempt first, then the `[E]`, then the teardown. The race direction decides, and `chat-subagent` loses it every time.
- **Why only `chat-subagent`, still open.** Two structural differences remain, both cheap to test later: (1) it has an extra `delegator` row BEFORE `tool-subagent`, whose persona work runs in the same `tools/change` dispatch; (2) its `tool-subagent` is a TOP-LEVEL row while every coding preset wraps its delegation rows in a `cordis:group`. `TODO.md` records the one-line discriminator (disable the `delegator` row, re-install, switch again) and the minimal upstream fix (do not cache a failed install, so the next `tools/change` retries).
- **Our side is unchanged.** The guard-only enforcement, the catalog boundary and the delegation path are untouched; no restriction was reintroduced. This release is otherwise documentation and version-only.

## [1.7.4] - 2026-10-17

### Fixed (`chat-subagent` sessions came up with NO delegation tool at all)

- **1.7.3's top-level mask collided with the official per-Agent install, and the collision cost the session its only tool.** A symptom reported from a live `dev_web` session was `[E] scope Error: tool "list_subagent_models" is already registered in this scope`, reached through `registerListSubagentModels()` (`@deepseek-ai/dsh-tool-subagent` `src/list-models.ts:87`) from `install()` (`src/index.ts:360-362`) via the per-Agent injection callback (`:676`). `install()` registers the lister BEFORE it calls `mount()`, so the throw meant `subagent` was never registered — the session had neither entry, which is exactly what the Tools tab showed.
- **The cause is that `restrict()` notifies `tools/change` and `guard()` does not.** `tools.restrict()` installs through `ScopedLayers.effect` with `notify` defaulting to `true` (`packages/core/scope/src/store.ts:226-266`), while `tools.guard()` passes `notify: false` (`packages/core/tools/src/index.ts:1136-1142`). `@deepseek-ai/dsh-tool-subagent` installs into a LIVE Agent on `tools/change` (`src/index.ts:693-698`), so the agent-scope restriction that 1.7.3 installed from `agent/created` pulled that reconciler into the creation window: one agent scope got TWO installs, the second threw the duplicate-name error above, and the first one's `mount()` never completed either. The same symptom was recorded in `TODO.md` from the previous attempt as "registration collision, the session gets no delegation tool".
- **`presets/chat-subagent/delegator.mjs` now installs a guard and NO restriction.** Enforcement is one `ctx.tools.guard(...)` on the preset's STANDING scope, and it branches on the CALLING agent's delegation depth — a guard is read from that agent's chain (`guardReason()` walks `chainLayers(exec.agent)`, `:1145-1154`), so one install covers the root session (`subagent` + `list_subagent_models`, plus PTC's `run_code` transport) and every delegated child (its declared read-only names + the lister). `installRestriction()` and `installInheritedSeal()` are gone; the module no longer touches `restrict()` at all, so it emits no `tools/change` in any creation window and the interleaving cannot recur.
- **The catalog is the price, and it is now documented as such.** The top-level session SEES this preset's rows (`read`, `write`, `edit`, `glob`, `grep`, `todo_*`, `job_*`) and may call none of them — the same "listed but refused" boundary `chat-agent` already documents for a profile's own-plane Team tools. `delegation-note.md` tells the model outright that a call to any of them is refused and that reading is what `subagent` is for, and the top-level refusal text is now instructive rather than a bare denial.
- **The per-agent install that remains is the persona alone**, and it still needs both directions of `tools/change` reconciliation plus the row-disposal and `agent/disposed` lifts (an agent-scope registration outlives the composition that asked for it, the 1.7.2 fix). The guard needs none of that: it lives on the standing scope and goes away with the composition.
- **`check-delegator.mjs` pins the new design instead of the old one.** Its fake tools service THROWS on `restrict()`, so any regression that reintroduces a restriction fails the check rather than a live profile; it asserts the single standing guard and both depth branches (root refuses `read`/`write`/`bash`/`spawn_teammate`, child refuses `write`/`bash`/`subagent`, both allow `run_code`, and a call that carries no agent is left alone), the per-agent persona and its lift, the absence of any per-agent tool install, and the row's `modelSelectionSettings: true`.
- Docs: `README.md` / `README.zh.md` / `CONTEXT.md` replace the per-agent mask description with the standing guard (**Agent-scope mask** becomes **Delegation guard**), state the catalog boundary, and drop the runtime probe. `TODO.md` records the confirmed upstream defect with this call stack.

## [1.7.3] - 2026-10-17

### Changed (`chat-subagent` can name the child's model too)

- **The preset's delegation row now carries `modelSelectionSettings: true`, so a chat session gets the optional `provider`/`model`/`reasoning_effort` parameters and the read-only `list_subagent_models`.** Its founding invariant reads "exactly one tool that ACTS" from here on: the catalog holds two entries, one acting and one read-only. Before this, the session answered "`subagent` only accepts `description` and `prompt`" — the flag was off, and leaving the discovery tool out was the only way to keep the catalog at one entry.
- **The flag cannot simply be turned on: it RELOCATES the tool.** With the opt-in, `@deepseek-ai/dsh-tool-subagent` installs `subagent` (and the lister) in each Agent's OWN layer, not on the preset's standing plane. `restrict()` validates only names a scope can INHERIT (`packages/core/tools/src/index.ts:1194-1201`) and own-layer registrations sit outside every restriction (`:1202-1208`), so `restrict({ allow: ['subagent'] })` would have thrown `names unknown global tool "subagent"`, the probe would have dropped the name, and the whole inherited surface would have stayed in the catalog. This is the coupling that kept the flag off, and the previous release reverted an attempt to route around it.
- **`presets/chat-subagent/delegator.mjs` now decides the top-level mask from the registry at runtime.** A silent probe asks whether the delegation tool is inherited. It is not on the opt-in path, so the mask seals the inherited surface with `restrict({ allow: [] })` (the `chat-agent` one-liner, own-layer registrations survive it by design) and the guard — which allows `subagent` and `list_subagent_models` — refuses every other call. On a `dsh-tool-subagent` older than the opt-in the tool IS inherited, so the mask keeps the named allow-list and warns once that this build cannot name a model: the preset keeps working instead of ending up with no tool at all. A delegated child's guard allows the lister too, so its catalog never lists a tool that would always refuse.
- **Docs, the shipped delegation note and the checks follow.** `delegation-note.md` — half of the top-level session's whole prompt — describes the two tools and the optional route. `check-subagent-model-selection.mjs` asserts the opt-in on `chat-subagent` instead of its absence. `check-delegator.mjs` covers both registration paths, the `allow: []` seal, `installInheritedSeal()`, and the lister in both guards.

## [1.7.2] - 2026-10-17

### Fixed (a session that LEFT `chat-subagent` kept its mask)

- **`presets/chat-subagent/delegator.mjs` now LIFTS the mask when an agent stops composing the preset.** What the delegator registers it registers on the AGENT's own scope (`agent.ctx`), which outlives the composition that asked for it: the blank-session preset switch goes `agentPresets.select` → `recompose` → `mount` + `emit('tools/change')`, and disposing the previous revision's standing scope does not reach an agent-scope registration. `tools/change` reconciliation covered only the arriving direction, so a session created on `chat-subagent` — the preset picker's previous selection — and then switched to a coding preset kept the delegation guard and answered `list_subagent_models` with `This session is a delegator-only preset: subagent is the only tool`. Found live on `dev_web`, in a `pair-coding-agent` session.
- **Every install records its disposer, so everything that installs can undo itself.** `installRestriction()` returns `{ kept, dispose }` and `installGuard()` returns the guard's disposer; the depth-0 persona section and its `suppressRuntimeContext()` are collected the same way. `reconcile()` lifts for agents that no longer compose the preset, `agent/disposed` frees the entry, a failed install lifts what did land instead of leaving half a mask, and disposing the row (HMR, a re-mounted revision, a removed patch) lifts everything it installed.
- **A mask is refused for a composition that names a DIFFERENT preset**, while an agent that has joined none — `composedPreset()` answers `undefined`, e.g. a delegated child before its join — is still masked. `check-delegator.mjs` gained the lift, the re-mask after a switch back, the foreign-creation refusal, the pre-join child, row disposal, and agent disposal.

### Added (a terminal line per delegated child)

- **`presets/shared/subagent-route-log.mjs`, mounted by the five coding presets, logs one `info` line per delegation: `<presetId>/subagent-route-log: subagent <id> route <provider>/<model>`.** A child's route is either named by the call — `provider`/`model` from the Host's authorized list, the 1.7.1 opt-in — or inherited from the parent session, and until now nothing on the terminal said which one did the work; the only way to find out was to open the child's session. Top-level sessions print nothing; `unknown` appears only when the harness stated neither half of the route; a row without `presetId` still logs, with one warning that the lines carry no preset name.
- **The line's two readers live in the shared module, not in one preset's directory.** `depthOf()` and `childRoute()` moved out of `presets/chat-subagent/delegator.mjs`, which now imports and re-exports them (`import { childRoute, depthOf } from '../shared/subagent-route-log.mjs'`), so the delegator and the five presets read a route the same way and there is one implementation. `chat-subagent` does not mount the row: its `delegator` prints the same line as part of masking the child, and a second row would duplicate every child. `check-subagent-route-log.mjs` (new, repository root) pins the shared identity, the depth read, the route halves including the Session-projection precedence, the per-child line, the missing-`presetId` warning, and each preset's row naming itself.

## [1.7.1] - 2026-10-17

### Added (the five coding presets can name the child's model)

- **`modelSelectionSettings: true` on the `tool-subagent` row of `qwencode-coding-agent`, `iflow-coding-agent`, `iflow-cre-agent`, `pair-coding-agent` and `codex-coding-agent`.** The flag is `@deepseek-ai/dsh-tool-subagent`'s Host-owned opt-in (`src/index.ts:109`, default `false`); with it off the tool schema has no route parameters at all and the child always inherits the parent session's route (`install(ctx, undefined)`, `:608-611`). With it on, the top-level Agent also gets `list_subagent_models`, and `subagent` accepts `provider` / `model` / `reasoning_effort`, constrained to the Host `subagent-model-selection` setting's authorized list — an explicit route outside that list fails with a message listing the available ones. This is the same one-key opt-in the shipped `standard`/`ptc`/`cordis` presets carry; `chat-subagent` keeps its flag off (the shared discovery tool would break its one-tool invariant, `presets/chat-subagent.patch.yml:49-50`) and `chat-agent` mounts no tool row at all. `subagent_fork` and the disabled `codex`/`claude-code` rows stay off, as upstream.
- **The opt-in is a Host dependency, not a self-contained capability.** Its provider is the profile's `@deepseek-ai/dsh-tool-subagent/model-selection-settings` row (mounted by the shipped `dsh-base` + `dsh-web-app` stack); without it the opting-in preset fails to mount **as a whole** — one failed row marks the preset broken. An absent setting row is not the same as a disabled setting: with the switch off the policy is simply undefined and the child inherits, so the fallback never errors. Both READMEs now name the dependency and its symptom in their Requirements sections, next to a new "Subagent Model Selection" subsection.
- **`check-subagent-model-selection.mjs` (new, repository root) pins it: `node check-subagent-model-selection.mjs`.** It asserts that the five spawn rows carry the flag exactly once each, that no `tool-subagent-fork` row does, that `chat-subagent`'s config key stays absent while `chat-agent` mounts no delegation row, and that both READMEs keep naming the Host plugin the opt-in depends on. Not listed in `files`, so it does not ship.

## [1.7.0] - 2026-10-15

### Added (a seventh preset: a chat session whose one tool delegates)

- **`presets/chat-subagent.patch.yml` — 通用聊天模式 · 可派活 (`id: chat-subagent`, `order: 16`), derived from `chat-agent`.** Its top-level session sees exactly **one** model-facing tool, `subagent` (`@deepseek-ai/dsh-tool-subagent`, `provider: spawn`, `enableRunInBackground: false` so `run_in_background` is not in the schema at all, `maxDepth: 1`). `modelSelectionSettings` is deliberately off: it would register the shared `list_subagent_models` tool and break the one-tool invariant. That single call waits for the child and returns its report.
- **The delegated child is what works, and it works read-only.** The child inherits the preset's own rows — `tool-fs`, `tool-fs-search`, `tool-todo`, `tool-jobs` — and is bounded by the declaration's `config.subagentTools`: by default `read`, `glob`, `grep`, `read_image`, `list_directory`, `todo_write`, `job_list`. No `bash`, no `write`, no `edit`: it investigates and reports. The declaration's `persona` (the row's per-child persona, applied by `applyChildComposition`) frames it, and the child keeps its runtime context and DSH's own `SUBAGENT_DELEGATION_CONTEXT` statement. `tool-todo` carries `allowParallelInProgress: true` — the one key `@deepseek-ai/dsh-tool-todo` marks `.required()` with no default, so a row without it fails to mount and the whole preset reports a load failure (found live on the `dev_web` profile; `check-delegator.mjs` now pins the key).

### Added (the two masks, and why they cannot live in the declaration)

- **`presets/chat-subagent/delegator.mjs` installs both masks on each AGENT's own scope, from `agent/created` and from `tools/change` reconciliation.** A preset-plane mask was the obvious shape and the wrong one: every Agent selecting a preset is parented to the revision's standing scope (`agent-preset-registry/src/index.ts:104-110` `createScope` + `mountPreset`), and a delegated child is parented to that **same** standing scope — `applyChildComposition` calls `agentPresets.composeFrom(childCtx, parent.ctx)` (`packages/subagent/subagent/src/child-agent.ts:200-219`). `ToolRuntime.view()` intersects the restrictions of every layer on the chain (`packages/core/tools/src/index.ts:1178-1201`), and a restriction can only narrow, so a standing `allow: ['subagent']` would have left the child with one tool and no work to do. `tools.restrict()` itself refuses an unscoped caller with this instruction — "deny the tool for the intended agent instead" (`:1097-1100`) — and a child's scope parent is the standing scope, never the parent Agent's (`agent-preset-registry/src/mount.ts:119-127`), so the agent-scope mask is exactly what a delegated child does not inherit. `agent/created` is awaited by the creation transaction before publication (`packages/core/agent/src/index.ts:537-559`), so the mask precedes the first request.
- **`tools/change` reconciliation is not optional.** The Web UI can switch a BLANK session's preset, which runs `agentPresets.select` → `recompose` → `mount` + `emit('tools/change')` and emits **no** `agent/created` (`agent-preset-registry/src/index.ts:306-334`). Without reconciliation that path would hand the user an unmasked session with the preset's whole tool set. The same listener covers a re-mounted revision, and `mask()` is idempotent (a `WeakSet`).
- **The guard closes the plane no restriction reaches.** Registrations in an agent's OWN layer are exempt from every restriction, so a top-level session on a profile that mounts the agent-team bundle still **lists** nine Team tools; the guard refuses their execution, exactly as `chat-agent`'s does. It also always allows `run_code`, PTC mode's model-direct transport: denying it would leave a PTC-mode session unable to call its single tool, while the restriction still bounds what the nested dispatch can bind (`restrict()` cannot name that transport at all — `:1111-1112`).
- **Depth decides which mask applies**, read the way `dsh-subagent` reads it (`packages/subagent/subagent/src/depth.ts:28-36`, header as the monotone floor): depth 0 gets `allow: ['subagent']`, the guard, a `complete: true` persona section and `suppressRuntimeContext()`; every deeper agent gets the `subagentTools` list and a guard that denies everything outside it. - **Do not "simplify" the two-plane mask in `no-tools.mjs`.** Dropping `restrict({ allow: [] })` re-admits the global layer and every ancestor scope (including tools a later bundle mounts); dropping the guard re-admits every agent-own registration, which is exactly this leak. Clearing `assembly.tools` in a `system-prompt/assemble` listener was considered and rejected: it would hide the catalog while leaving the tools executable, and it depends on watermark ordering against every other listener.

  - `codex-collab-mode.mjs` was reading `ref/codex-default-mode.md` and `ref/codex-plan-mode.md` at module-load time with top-level `readFileSync` calls. If the installed location did not have the `ref/` directory next to the plugin file, the dynamic import threw ENOENT before `apply()` ever ran, the plugin failed to mount, and the preset composition rejected. The read now happens lazily inside `apply()` with an ENOENT fallback to an empty string + a `console.warn`, so the plugin imports cleanly even if the `ref/` files are absent. `ref/` remains the canonical source when present.
  - `codex-permissions.mjs` declared `inject: ['systemPrompt', 'agents']` but used `ctx.sandboxPolicy` and `ctx.approval` (both undeclared). Added `'sandboxPolicy'` and `'approval'` to the `inject` array.
  - `codex-collab-mode.mjs` declared `inject: ['systemPrompt', 'planMode', 'agents']`. `agent.cordis.yml` mounts `@deepseek-ai/dsh-plan-mode` inside the `planning` group with `isolate: { planMode: true }`, which scopes the service to that group's entry-local realm — a consumer outside the group cannot reach it (Cordis skill doc, "The rule that catches people"). Mount-validation rejects the row as "did not activate: waiting for planMode" and the whole preset composition fails. Even after dropping `'planMode'` from `inject`, touching `ctx.planMode` at runtime throws `cannot get property "planMode" without inject` at property-access time, which no try/catch can intercept. So the plugin must never read `ctx.planMode`: it now unconditionally emits the default-mode body on every step. The plan-mode body still lives at `ref/codex-plan-mode.md` (read lazily at apply time) so a future DSH release that exposes `planMode` on the outer ctx can resume the swap by adding `planMode` back to `inject` and reading it. Plan-mode messaging on the model side continues to come from `dsh-plan-mode`'s section under the `planning` group, which renders the same upstream `plan.md` content as a system-prompt section.

### Known limitations (DSH platform constraints)
- **Input[] role degradation**: upstream Codex uses `role: 'developer'` for the `<permissions instructions>` and `<collaboration_mode>` blocks. DSH currently only supports `role: 'system' | 'user' | 'assistant'` (see `packages/llm/llm/src/message.ts:131-135`), so `codex-permissions.mjs` and `codex-collab-mode.mjs` degrade to `user`-role. Each of the three new `.mjs` files carries an `UPGRADE NOTE` at the top of its source explaining the migration: swap `createUserMessage` for a developer-role factory when DSH adds one. `codex-environment.mjs` is already at parity (upstream `<environment_context>` is `user`-role).
- **No DSH wrapper**: unlike the DSH-native `systemPrompt.context()` path (which forces a `Current runtime context. This snapshot supersedes earlier runtime-context snapshots.` prefix and a flat join), the `agent/pre-step` listener approach injects the three Codex blocks as raw `user/message` events with verbatim `<permissions instructions>`, `<collaboration_mode>`, and `<environment_context>` markers — no wrapper, no nesting.
- **DSH sandbox/approval not double-rendered**: `codex-permissions.mjs` calls `ctx.systemPrompt.suppressRuntimeContext()` to silence the DSH-native `sandbox:policy` and `approval:policy` contexts. This is an all-or-nothing suppressor, but only `ctx.systemPrompt.context()` registrations fall to it; harness sections (`harness:source`, `app:web-surface`, persona suffix) and the `time-context` package's `agent/pre-step` listener are unaffected.

### Changed (instruction-echo mitigation)
Three prompt rules in `pair-coding-agent/agent.cordis.yml` were rewritten to positive framing to avoid instruction echo — the tendency of "do not X" rules to prime the model toward X by repeatedly naming the unwanted behavior:
